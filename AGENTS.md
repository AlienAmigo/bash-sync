# AGENTS.md — инструкции для ИИ-агентов

## О проекте

`bash-sync` — модульная система конфигурации bash с синхронизацией между машинами через Git. Конфиг загружается из `~/.bashrc` → `config/main.sh` → модули по фазам → `~/.bashrc_local` (локальные переопределения, последними). Подробности архитектуры — в `readme.md`.

## Критичное правило: формат вывода — только по согласованию

**Любые изменения, влияющие на то, что пользователь видит в терминале, нужно СНАЧАЛА согласовать с пользователем.** Это относится к:

- цветам (`config/colors.sh`, переменные `CL_*`, ANSI-коды `\033[...]`, в т.ч. локальные `RED`/`GREEN`/... в скриптах);
- текстам сообщений (`config/messages.sh`, переменные `MSG_*`, и любые строки `echo`/`echo -e`);
- приглашению командной строки (PS1, сборка в `.bashrc`, SECTION 6);
- приветствию при загрузке конфига (конец `config/main.sh`);
- выводу при старте сессии (ssh-agent блок в `.bashrc`, SECTION 8);
- составу выводимой информации (добавление/удаление строк вывода, эмодзи, символы `✓`/`✗`/`▶`, форматирование).

Порядок действий: сначала показать пользователю предлагаемый вид вывода (как строка будет выглядеть), получить подтверждение — и только потом менять код. Это важно, потому что конфиг синхронизируется на все машины пользователя и вывод виден при каждом запуске терминала.

Это правило НЕ запрещает менять логику: если поведение функции меняется без изменения её вывода — согласование не требуется.

## Правила безопасности

- **Никогда не коммитить секреты.** Токены, пароли, ключи — только в `~/.bashrc_local`, который не входит в репозиторий.
- `~/.bashrc_local` и содержимое `~/.bash_backup/` — машинно-специфичны, в Git не попадают.
- Скрипты `install.sh` / `update.sh` создают бэкапы в `~/.bash_backup/` автоматически — не отключать этот механизм.
- `uninstall.sh` меняет `~/.bashrc` пользователя — любые правки этого скрипта требуют особой осторожности.

## Соглашения по коду

- Цвета — только через переменные `CL_*` из `config/colors.sh`; в `config/`-модулях не хардкодить ANSI-коды. (Исключение, существующее исторически: `scripts/*.sh` используют локальные `RED`/`GREEN`/... — при правках сохранять этот стиль.)
- Тексты сообщений — через переменные `MSG_*` из `config/messages.sh`.
- Переходы по директориям — через `cd_safe()` из `config/helpers.sh`, а не голый `cd` в алиасах.
- Порядок загрузки модулей задан в `config/main.sh` (config → colors → messages → helpers → paths → os/* → git → aliases → `.bashrc_local`). Новый модуль добавлять через `_safe_source` в соответствующую фазу; алиасы грузятся последними, т.к. используют всё предыдущее.
- После `.bashrc_local` `paths.sh` применяется повторно: производные пути пересчитываются с учётом локального `PROJECTS_ROOT` и переопределённых функций `*_path`. Поэтому машинно-специфичные переопределения делать через `PROJECTS_ROOT` или функции, а не через прямой экспорт производных переменных в `.bashrc_local`.
- Функции/алиасы, зависящие от путей, должны использовать переменные из `config/paths.sh` (`PROJECTS_ROOT`, `WORK_ROOT` и т.д.) с дефолтом `${PROJECTS_ROOT:-$HOME/Projects}`, чтобы работать на машине без `paths.sh`.
- OS-специфичное — только в `config/os/{windows,linux,macos}.sh`; определение ОС — через `$OSTYPE` / `BASH_CONFIG_OS`, не дублировать логику.
- Внутренние служебные функции в `main.sh` именуются с подчёркивания (`_log`, `_safe_source`) и удаляются через `unset -f` после загрузки, чтобы не засорять namespace.
- Файлы в репозитории должны быть кроссплатформенными: не использовать Windows-специфичные пути вне `config/os/windows.sh`.

## Тестирование изменений

Автоматика:

```bash
bash tests/smoke.sh      # smoke-тест: загрузка конфига, ОС, алиасы, переопределение путей
shellcheck .bashrc config/*.sh config/os/*.sh scripts/*.sh tests/*.sh
```

CI (`.github/workflows/test.yml`) прогоняет оба на push в `main` и PR, smoke-тест — на матрице Ubuntu / macOS / Windows (Git Bash). Замечания shellcheck не глушить массово: чинить или точечно отключать с комментарием.

Ручная проверка:

```bash
source ~/.bashrc          # или reload — перезагрузка конфига
bshtest                   # базовый тест: BASH_CONFIG_LOADED, пути, алиасы
paths                     # показать текущие пути
```

Отладка загрузки модулей:

```bash
export BASH_CONFIG_DEBUG=true && source ~/.bashrc
```

Лог загрузки: `${TMPDIR:-/tmp}/bash_config_<user>.log`.

Проверять на всех поддерживаемых ОС (Windows Git Bash / Linux / macOS) или явно указывать пользователю, на чём проверено, а на чём — нет.

## Git-воркфлоу

- Рабочие ветки: отдельные ветки под задачи (`bug-fixes`, `module`, ...), слияние в `main`.
- После изменений в репозитории пользователь применяет их на машине через `scripts/update.sh` + `source ~/.bashrc`.
- Алиас `gpom` пушит в `master`, но основная ветка репозитория — `main`; при автоматизации пушей использовать актуальную ветку, не хардкодить.

## При изменении этого файла

Если меняется структура проекта, порядок загрузки модулей или правила выше — обновлять `AGENTS.md` и `readme.md` синхронно.
