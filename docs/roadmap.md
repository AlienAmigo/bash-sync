# Roadmap исправлений

План работ по итогам ревью проекта (2026-11-27). Пункты сгруппированы по
приоритету: P0 — баги, P1 — соответствие собственным правилам, P2 —
архитектура, P3 — чистка.

Обозначения:

- **[вывод]** — пункт меняет то, что видно в терминале: по правилу AGENTS.md
  вид вывода сначала согласуется с пользователем, потом меняется код.
- **[docs]** — пункт требует синхронного обновления `AGENTS.md` и `readme.md`.

Каждый пункт после реализации проверяется стандартно:

```bash
bash tests/smoke.sh
shellcheck .bashrc config/*.sh config/os/*.sh scripts/*.sh tests/*.sh
```

## P0 — баги

### 1. Изоляция smoke-теста

**Проблема.** `tests/smoke.sh` заявляет полную изоляцию (комментарий в шапке),
но подменяет только `HOME`. Дочерний bash наследует экспортированные
переменные текущей сессии (`PROJECTS_ROOT` и др.), поэтому на машине с
загруженным конфигом проверка «default PROJECTS_ROOT falls back to
~/Projects» падает. Воспроизведено: 14/15 локально, 15/15 в `env -i`.

**Где:** `tests/smoke.sh:36`, `tests/smoke.sh:51`.

**Решение.** Запускать дочерние проверки через
`env -i HOME="$TMP_HOME" PATH="$PATH" TERM="${TERM:-dumb}" bash -c ...`
(переменные `TERM`/`OSTYPE`-зависимые проверки учесть: `OSTYPE` bash
выставляет сам, `BASH_CONFIG_OS` для теста preset-режима передавать явно).

**Проверка.** `bash tests/smoke.sh` зелёный и в чистом окружении, и в сессии
с загруженным конфигом (`source ~/.bashrc && bash tests/smoke.sh`).

### 2. GNU-флаги `ls` ломают алиас на macOS

**Проблема.** Алиас использует GNU-only флаги (`--block-size=K`,
`--group-directories-first`, `--color=always`); на BSD ls (macOS) команда
падает. README при этом заявляет поддержку macOS.

**Где:** `config/aliases.sh:11`.

**Решение.** Определять алиас условно: GNU-вариант при наличии GNU ls
(проверка `ls --version` / `$BASH_CONFIG_OS`), BSD-вариант
(`ls -G -cvA` или через `CLICOLOR`) для macOS. Вариант — перенести
специфичную часть в `config/os/*.sh`.

**Проверка.** На macOS: `ls` работает без ошибок. Smoke-тест дополнить
проверкой, что алиас `ls` исполняется (не только определён).

### 3. `apt`-алиасы применяются ко всему Linux

**Проблема.** `update`, `cleanup`, `search`, `show` используют `apt` и
вешаются на любой Linux, включая заявленный в README CentOS.

**Где:** `config/os/linux.sh:5-6`, `config/os/linux.sh:19-20`.

**Решение.** Устанавливать алиасы только при наличии `apt`
(`command -v apt`) или по ID дистрибутива из `/etc/os-release`.
Заодно решить судьбу CentOS в README: либо добавить `dnf`-варианты,
либо убрать CentOS из списка поддерживаемых.

**Проверка.** `source` на системе без `apt` не создаёт битые алиасы.

## P1 — соответствие собственным правилам

### 4. Windows-путь в `.bashrc` (dev-mode)

**Проблема.** Кандидат `/d/Project/bash-sync` — Windows-специфичный путь
вне `config/os/windows.sh`; AGENTS.md это прямо запрещает.

**Где:** `.bashrc:111`.

**Решение.** Формировать список кандидатов из `$HOME`-относительных путей
плюс опциональная переменная `BASH_SYNC_DEV_DIR`, задаваемая в
`.bashrc_local`. Windows-машины прописывают свою папку локально.

**Проверка.** Dev-режим активируется при `BASH_SYNC_DEV_DIR` и при
`~/bash-sync`; без них — production-режим.

### 5. Хардкод цвета в приветствии **[вывод]**

**Проблема.** Приветствие использует `\033[0;32m` в обход `CL_*` — нарушение
соглашения о цветах в `config/`-модулях.

**Где:** `config/main.sh:160-161`.

**Решение.** Заменить на `${CL_GREEN}...${CL_RESET}`. Визуально цвет тот же,
но вид строк сначала показать пользователю (правило AGENTS.md).

### 6. Алиас `gpom` пушит в `master`

**Проблема.** Основная ветка репозитория — `main`; `gpom` = `git push origin
master`. AGENTS.md фиксирует проблему, но алиас остаётся ловушкой.

**Где:** `config/aliases.sh:47`.

**Решение.** Согласовать с пользователем **[вывод]**: удалить алиас или
переопределить как `git push origin main` (рабочие проекты пользователя могут
использовать `master` — тогда оставить и зафиксировать в README назначение).

## P2 — архитектура

### 7. Выделить рабочую специфику в отдельный модуль **[docs]**

**Проблема.** Алиасы и пути конкретных проектов (osmohub, stroybase, tsus,
Laravel/docker-команды) зашиты в общие модули — репозиторий нельзя
опубликовать/зафоркать без чужой рабочей специфики.

**Где:** `config/aliases.sh:72-100`, `config/paths.sh:25-33`,
`.bashrc:76-101` (ANDROID_HOME, JetBrains, nvm).

**Решение.** Новый модуль `config/work.sh` (алиасы + функции путей),
загрузка через `_safe_source` в `main.sh` по флагу
`CFG_LOAD_WORK=true|false` (дефолт согласовать). Машинно-специфичные
экспорты из `.bashrc` (ANDROID_HOME и т.п.) перенести в шаблон
`.bashrc_local`. Обновить порядок загрузки в `AGENTS.md` и `readme.md`.

**Проверка.** Smoke: при `CFG_LOAD_WORK=false` алиасы `osmohub` нет, конфиг
грузится без ошибок; при `true` — поведение как раньше.

### 8. Режим установки по симлинку

**Проблема.** install/update копируют `config/` в `~/config` и заменяют
`~/.bashrc`: два источника правды, правки в `~/config` разъезжаются
с репозиторием, ручные изменения `~/.bashrc` молча затираются при update.

**Где:** `scripts/install.sh:37-48`, `scripts/update.sh:46-61`.

**Решение.** Флаг `--link`: `~/config -> <repo>/config` и
`~/.bashrc -> <repo>/.bashrc` (с теми же бэкапами). update.sh при
симлинках ограничивается `git pull`. README уже упоминает симлинк в
траблшутинге — дописать установку.

**Проверка.** Установка `--link` в тестовый HOME, правка файла в репо видна
без update.

### 9. SSH-блок: документировать и сделать управляемым **[вывод]**

**Проблема.** Авто-`ssh-add` всех ключей запрашивает passphrase при каждом
новом шелле для зашифрованных ключей; на macOS каждый таб терминала создаёт
новый агент. Поведение нигде не описано.

**Где:** `.bashrc:194-227`.

**Решение.** Флаг `CFG_SSH_AUTOADD=true|false` (дефолт — текущее поведение,
согласовать). Описать механику в README. Вывод `Agent pid`/`ssh-key added`
не менять без согласования.

## P3 — чистка

### 10. Удалить мёртвый `load_os_config()`

Не вызывается нигде, ссылается на legacy-механизм `~/.bash_config_$os`.
`config/helpers.sh:29-38`.

### 11. Починить или убрать счётчик ошибок в `_post_load_validation`

`errors=0` никогда не инкрементируется, `return $errors` всегда 0.
Либо инкрементировать при WARN, либо упростить до предупреждений без кода
возврата. `config/main.sh:115-137`.

### 12. Использовать `BASH_CONFIG_LOAD_TIME`

Сейчас выставляется и не используется. Вариант: при
`BASH_CONFIG_DEBUG=true` показывать время загрузки конфига **[вывод]** —
или удалить переменную. `config/main.sh:152-153`.

### 13. `uninstall.sh`: полная чистка секции без бэкапа

Fallback-sed удаляет только строку заголовка SECTION 5, а не весь блок
до следующей SECTION — в `~/.bashrc` остаются обрывки. Удалять диапазон
между маркерами `SECTION 5` и `SECTION 6`. `scripts/uninstall.sh:44-53`.
Осторожно: правки этого скрипта — особая зона риска по AGENTS.md.

### 14. `docker-stop` падает без запущенных контейнеров

`docker stop $(docker ps -qa)` при пустом списке возвращает ошибку.
Обернуть в функцию с проверкой. `config/aliases.sh:95`.

### 15. Актуализировать README по поддерживаемым системам **[docs]**

После пунктов 2–3: привести список «Поддерживаемые системы» в README
в соответствие с фактическим поведением (CentOS, macOS).

## Порядок работ

1. P0 целиком — это баги, каждый в отдельной ветке (`bug-fixes` или
   `fix/<имя>`), после каждого — smoke + shellcheck.
2. P1 — короткие правки, пункты 5–6 только после согласования вывода.
3. P2 — по одному пункту на ветку (`module`, `install-link`), каждый
   затрагивает документацию.
4. P3 — можно пакетом в одной ветке `cleanup`.
